# KAYAN offline fact provenance v1 proposal

20 November 2026 · Design for review

Use a case-scoped registry and one Windows Security Event XML parser. Start with Event 1102 v0 and Event 4624 v2. Both use the same exported record format. 1102 is a concrete action-and-outcome example aligned with the existing cedar fixture. 4624 gives a narrow way to test the distinction between finding a session candidate and establishing the actor of an event. Neither record alone establishes adversary control or organizational authorization. [Microsoft Event 1102](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-1102) · [Microsoft Event 4624](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4624)

## Existing baseline

V3 uses a reviewed occurrence key and compares source strings for independent attribution. V4 resolves one cited mechanic per technique within the selected case and evaluates the entire reviewed event for uncited adverse evidence. Its fact type carries a categorical actor and session string. The synthetic slate fixture demonstrates that one statement can have two correct event associations. Its tests establish the guard behavior with supplied assignments, including cross-case isolation and competing anchors. They leave raw identity, chronology and provenance unverified. ## Minimal versioned representation

Use local JSON manifests and immutable payload files. Each manifest declares `schema_version = "kayan.offline-evidence/1"` and a case ID. Reject unknown schema versions, duplicate keys and orphan references. IDs are opaque, case-scoped unless a row explicitly declares a wider identity namespace. Record and review revisions are append-only. Use typed unknowns of the form `{state: unknown | unresolved, reason: …}` or `{state: known, value: …}` where a field may be unavailable. Missing, malformed, conflicting and coverage-gap states must be distinguishable.

| Record type | Required fields and relationships |
| --- | --- |
| Original observation | `case_id, record_id, revision, raw_sha256, byte_length, media_type, source_id, native_record_ref, collected_at, supersedes?`. The native locator includes stream or export generation, channel and record number when known. Pin the manifest digest outside the import directory or authenticate the manifest through the review channel. Hash exact bytes before parsing. |
| Source lineage | `source_id, observed_alias, canonical_collector_id, origin_family_id, upstream_source_ids, lineage_revision, attestation_ref`. Resolve through a case-owner-pinned catalogue. Different relays of the same upstream origin share an origin family. Two independent-looking names count as one origin if their lineage overlaps. Unknown lineage prevents an independence decision. A raw hash match is a duplicate signal, not the criterion for proving independence. |
| Exact statement | `statement_id, record_id, revision, raw_sha256, locator`. XML locators use namespace-aware paths with exact occurrence and attribute selection. Narrative fixture locators use UTF-8 byte ranges. Resolve against the immutable revision and return the original field or source text with a case-local display citation. Edited excerpts and reused display addresses cannot retarget a link. |
| Deterministically normalized observation | `normalizer_id, version, input_digest, typed_fields, field_to_statement_refs, diagnostics`. Preserve the original precision and source of each value. These rows can represent what a source recorded and can propose mechanical joins. |
| Reviewed event | `case_id, event_id, revision, tenant_ref, asset_ref, principal_ref, session_ref, time, status`. A principal key is tenant plus identity authority plus stable account ID. A session key is tenant plus asset plus validated session generation plus native session ID. Source tokens may be retained when a resolved key is unavailable. `time` carries source time, time basis, precision and uncertainty bounds or reason. |
| Reviewed assertion and association | `association_id, case_id, event_id, event_revision, role, typed_value, statement_refs[], review_receipt_ref, revision, state, supersedes?`. Roles cover mechanic/action, objective, outcome, identity/linkage, authorization, attribution and adverse evidence. Evidence edges can declare joint necessity or separate sufficiency. Authorization records bind policy scope, actor, asset, action and validity interval. Adverse evidence explicitly represents contradiction, uncertainty, retraction or supersession. Each event-to-statement association is separately reviewed even when an identical statement helps two events. |
| Review receipt | `review_id, reviewer_id, reviewer_role, revision, reviewed_at, decision, rationale, input_snapshot_digest, assertion_set_digest, supersedes?`. Obtain through a separate write path from an enrolled reviewer independent of suggestion generation. Bind exact case, event, assertion, source and lineage revisions. The fixture uses a pinned synthetic reviewer catalogue and receipts to exercise this boundary. Fixture credentials establish no real reviewer independence. |
| Unverified suggestion | `suggestion_id, case_id, proposed_event?, proposed_value, proposed_statement_refs, producer, generation_ref?, status=unverified`. Store in a separate collection. A reviewer can inspect a suggestion and create a new reviewed assertion by independently checking the original evidence. An incoming review flag or valid signature from a suggestion producer confers no reviewer authority. |

Revision selection uses a pinned snapshot of active heads. Require an explicit predecessor chain within the same object and case. Reject forks or cycles pending adjudication. A correction or withdrawal leaves earlier bytes available for audit but invalidates affected active links until re-reviewed. The adapter passes applicable active vetoes even if the submitted proposal omits them. Indeterminate whether an adverse record applies means withhold the affected claim pending review.

## Windows Security Event XML profile

Accept one saved UTF-8 XML `Event` per observation under the Microsoft Windows Event namespace. Expected shape, namespace, provider GUID, Security channel, EventID and Version are a profile allow-list. Bound input size and depth, disable DTD/entity expansion and external resource access, and reject duplicate singleton fields. Unknown profiles remain retained originals with a normalization diagnostic. A malformed typed field cannot contribute a linkage key. Preserve the raw field and diagnostic even when the rest of the record remains usable. Embedded provider and computer strings are source assertions. The case catalogue supplies any trusted host, tenant, clock and origin mapping.

| Input | Supported normalization | Scope of meaning |
| --- | --- | --- |
| Common `System` fields | Provider name/GUID, EventID, Version, Channel, Computer, EventRecordID, `TimeCreated/@SystemTime`. Preserve fractional precision and parse UTC without dropping digits. Keep record numbers in their collection scope. | Reported event time and reported host. The timestamp does not identify the actor. Fractional precision does not establish clock accuracy. |
| Event 1102 v0, `Microsoft-Windows-Eventlog` | Read `UserData/LogFileCleared` in the documented payload namespace. Preserve `SubjectUserSid`, `SubjectUserName`, `SubjectDomainName`, `SubjectLogonId`. Normalize the latter as an unsigned hexadecimal value with the original lexeme retained. Emit a reported completed Security audit-log clear. | Subject SID and native logon ID describe the recorded subject. No proof of physical operator, hostile control, intent, organizational authorization or coverage of missing logs. |
| Event 4624 v2, `Microsoft-Windows-Security-Auditing` | Read named `EventData/Data` entries `TargetUserSid`, `TargetUserName`, `TargetDomainName`, `TargetLogonId` and `LogonType`. Preserve the distinction from `Subject*`. Emit a reported successful logon and its target session token. | A successful logon does not establish permission for a later clear, continuous control of the account or an independent source of attribution when the two events share their origin. |

[Microsoft Event 1102 XML and field semantics](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-1102) · [Microsoft Event 4624 XML and field semantics](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4624)

**Join rule.** Compare 1102 subject to 4624 target only after matching the pinned case, tenant, stable host, SID/authority and nonzero native logon ID. Limit consideration to the same independently identified session-generation scope and a fixture-defined time window. A clock conversion or uncertainty bound must have reviewed provenance. Represent the possible event instant as a half-open UTC interval that includes reporting precision and any clock error. Require the full 4624 interval to precede the 1102 interval for a definite order, with both within the known generation scope. Unknown error bounds, overlapping order, multiple plausible sessions or missing scope remain unresolved. A unique match is a linkage candidate until the reviewer establishes the association. For policy applicability require the full event interval within the reviewed authorization interval and exact scope match. Disjointness excludes that particular grant. Partial coverage or no matching grant leaves authority unresolved unless affirmative reviewed evidence establishes unauthorized action. Display names, time proximity, privilege level and event-log absence carry no authority.

## Trust flow and result contract

1. The case owner pins the observation manifest and approved lineage and reviewer catalogues. The loader verifies bytes and versioned references before exposing originals or normalizing fields.
2. The parser produces source observations and diagnostics. Only the independent reviewer path creates trusted associations. Review receipts bind the snapshot and the approved assertions. Research inference output, if present in a fixture, stays in the suggestion store.
3. The prototype adapter admits only independently reviewed associations from the verified active case snapshot. It resolves canonical origin family and emits existing `Fact` records with case-local citations. If two required proof sources have unresolved or overlapping origin, no independent attribution is projected. Preserve a reverse map to exact statements and review receipts. Stop on conflicting or unsupported projections rather than silently collapsing the evidence. Pass the full active reviewed event bank, including applicable adverse facts, to the existing v4 interface.
4. **V4 batch status means at least one finding is eligible.** The implementation returns `eligible_for_analyst_review` whenever `findings` is nonempty, even with entries in `rejected`. The proposed offline adapter exposes `batch_state = all_eligible | mixed | none_eligible | abstained | invalid` and counts, with one disposition per submitted technique and no batch approval flag. Determine all/mixed/none from explicit partition of requested claims. Missing or duplicated dispositions, unexpected claims or case mismatches invalidate the result. Serialize the event, citations and receipts for each eligible claim and explicit withholding reasons for each rejected claim. A consumer preparing analyst review items iterates eligible per-claim entries only. A consumer requiring a clean batch must check `all_eligible` and a nonempty expected claim set. A malformed envelope stays invalid, while a well-formed unresolvable citation can withhold just its claim. ## Fixtures and acceptance matrix

Start with two hand-authored Windows XML fixtures matching the documented paths. The synthetic 4624 has target SID `S-1-5-21-100-200-300-1104`, logon ID `0x55cd1d` and reported time 09:00 UTC. The synthetic 1102 has the same subject tokens at 09:10 UTC on the same reported host. The test catalogue binds it to tenant `blue`, asset `jun-4` and a reviewed generation spanning the events. Add one independently sourced, fixture-labelled custody statement and a separate authorization decision. Fixture receipt bindings over those statements supply the hostile control and unauthorized judgement that XML cannot provide. Use the unchanged slate fixture or a separate derivative fixture for shared associations and mixed verdicts. Pair each mutation with the expected per-claim outcome and rejection reason.

| Regression | Mutation and required result |
| --- | --- |
| Original integrity and references | Change one byte after pinning. Reject the record before normalization. Reject missing revision, bad namespace selector, invalid span and digest mismatch. Unsupported event version or duplicate singleton cannot provide proof. |
| Legitimate shared evidence | Bind a single reviewed statement independently to two slate occurrences. Both are eligible with their own provenance. Delete one association or borrow the sibling's outcome. Withhold that claim. |
| Cross-tenant identity | Add a red-tenant event with the same display name and optionally reused native logon token. No identity edge crosses the tenant. A mismatching SID on the same tenant/host also leaves the link unresolved. |
| Session ambiguity | Remove the native token or generation scope. Add a second plausible matching logon, or substitute 4624's reporting subject for its target. The clear remains a reported mechanic with no verified session link. |
| Time and coverage | Reverse or overlap possible event intervals, exceed the declared join window or cross a generation boundary. Withhold the link. Partial policy coverage and unknown clock bounds cannot establish applicable authority. |
| Authorization | With full matching scope and coverage, an authorized decision withholds the adversarial finding. A separately reviewed unauthorized decision allows eligibility only with all other proof. Missing or disjoint grant evidence alone stays unresolved. |
| Action outcome | A complete 1102 record emits reported completion. A separate reviewed failed or incomplete action fixture yields withholding. This negative fixture comes from a reviewed narrative, since 1102 alone does not encode failed clears. |
| Revision and contradiction | Bind an uncited active retraction or contradictory reviewed fact. Withhold the affected event. An unrelated event stays eligible. Reject stale or forked receipts and retain older evidence for audit. |
| Collector aliases | Present the same origin through two relays and vary the rendered XML or excerpt. Canonical lineage still prevents independent attribution. An actually independent origin with a valid receipt can satisfy it. |
| Review authority | Submit a perfectly formed model suggestion with valid references, a self-declared review flag, an unenrolled signer or a receipt for an earlier snapshot. None projects into trusted facts. |
| Mixed batch | Submit both slate claims with only one complete chain. The raw v4 status is eligible with a nonempty rejection map. The adapter emits mixed and admits exactly one review item. Test missing entries, duplicated decisions and empty batches explicitly. |

## Guarantees and assignment for approval

Deterministic checks can verify bytes against a trusted digest, resolve exact statements, enforce record/profile types, compare known identity keys and intervals, reject duplicated lineage, bind authorized review receipts, and keep dispositions per claim. The catalogue must still be established by a trusted owner. Human domain review determines whether a collector is genuinely independent, which principal controlled a session, whether a reported outcome reflects reality, whether organizational permission applied and whether cited evidence supports the asserted ATT&CK meaning. A study on authored fixtures establishes behavior under those inputs. Independent review and fresh telemetry are needed to assess external validity.

| Proposed file | Bounded responsibility |
| --- | --- |
| `eval/attack_fact_registry_v1.py` | Define versioned record, source, assertion and review types. Verify pinned snapshots, immutable references, revision heads, canonical lineage, enrollment and effective-reviewed facts. Keep suggestion ingress separate. |
| `eval/attack_windows_event_normalizer_v1.py` | Pure parser for the two XML profiles, source locators, typed time fields and a deterministic session-candidate check. |
| `eval/attack_fact_guard_adapter_v1.py` | Project reviewed evidence and reverse citation map into v4. Translate v4 to per-claim dispositions and explicit batch state. |
| `eval/fixtures/ai/attack_fact_registry_v1/` | New synthetic XML, lineage/review manifests and expected outcomes. Keep derivative slate materials separate from the frozen fixtures. |
| `tests/test_attack_fact_registry_v1.py`, `tests/test_attack_windows_event_normalizer_v1.py`, `tests/test_attack_fact_guard_adapter_v1.py` | Implement the acceptance matrix and confirm original guard suites and frozen artifact digests. |

**Approval scope.** Build the offline registry, parser and adapter against these fixtures. Provide one reproducible raw XML → normalized observation → reviewed facts → per-claim verdict demonstration. Acceptance requires every matrix mutation to yield its stated disposition, byte-for-byte reproducible normalization, full reverse evidence references, and independent fixture-backed review of the expected XML fields. Return source, fixtures, exact test results and unchanged historical artifact hashes. A real reviewer enrollment or data onboarding exercise requires separate approval. This proposal is the design checkpoint. Experiment E remains deferred.
