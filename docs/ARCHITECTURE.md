# Current architecture — checked 2026-11-01

The active implementation is a Rust TrustGate service, a Python local-Qwen execution engine, a Python console backend, and a separate TypeScript 3D console. Canonical paths, commands and evidence are in ../MASTER_HANDOFF.md.

1. ROE: integration/roe_signing.py and trustgate/service/src/roe.rs authenticate canonical contracts with HMAC-SHA256 using TRUSTGATE_ROE_KEY or the ignored data/roe_signing_key. Rust compiles roles, explicit action sets, targets and time windows into cedar-policy 4.14.0 policies.
2. Gate: Rust/Axum on 8000. Unknown actions/techniques default-deny; untrusted provenance and forbidden actions are rejected. Decisions enter the hash-chained, HMAC-signed audit file. The file is mutable storage, not immutable storage. Provenance labels are supplied by trusted callers; generalized semantic taint propagation is not proven.
3. Engine: pentagi/live_engagement.py uses real Ollama streaming JSON responses for Planner, Recon, Web-App, Network and Reporting decisions. Option A shares qwen2.5:7b, role prompts/contracts, one inference at a time; explicitly declared 1.5B fallback is only selected when 7B is absent. No model-selected arbitrary shell or URL executor exists. Bounded lab tools target http://127.0.0.1:8888 only. Findings require a fresh second request with supported evidence before publishing.
4. Operator/bus: console/backend/live_api.py authorizes operator input through TrustGate, queues task-changing instructions until a task boundary, and handles status questions via real model calls. Internal agent routing/acknowledgments require an HMAC bridge signature and enrolled agent IDs. Operator identity is a local label, not an authenticated remote login.
5. Console: FastAPI on 8001 persists full session snapshots and broadcasts initial/subsequent revisions over /ws. GET /agents/{agent_id}/session?engagement_id=... recovers current or saved sessions. The sole prepared 3D office now lives in console/office/, uses React Three Fiber/Three.js on 5173 and projects those snapshots; it has no independent engagement engine. The 2D fallback was retired during consolidation. Rust, Python, frontend and vendored scoped Go source now share the canonical repository, with HTTP/WebSocket boundaries retained.

Grounding uses TF-IDF over pinned ATT&CK/OWASP data and a pinned 818-packet third-party skills corpus. These are reference context, never permissions. No embeddings or fine-tuning are implemented. Full raw observations/context remain in the transcript; actual model-input excerpts are recorded separately and bounded for the 4096-token local context window.

The deterministic pentagi/orchestrator.py remains an explicitly labeled baseline. Its reported findings are not automatically verified exploits. The scoped upstream Go PentAGI boundary evaluation is complete with disclosed worker/adapter limits; Python is the primary demo path. A full Go runtime/console replacement is outside the current demo scope; see BLOCKED.md. No upstream sandbox/security claim is established for the Python process.

The live on/off evaluation found an action-selection regression with grounding. Do not claim a reasoning improvement, production identity security, automatic ROE revocation at engagement completion or immutable audit storage. Browser visual acceptance cannot be inferred from these engine results; separate dated rendered observations and their limits are in docs/CLOSURE_EVIDENCE_REVIEW_2026-11-01.md and docs/TA_MEETING_READINESS_2026-11-01.md.

Upstream Go local profile: integration/pentagi_binding.py issues a short-lived MAC-authenticated context from an actual signed ROE. The backend middleware/controller binds it to the authenticated user, and pkg/trustgate gates executor dispatch using actual actor/flow/task/subtask metadata. Only independently materialized signed local command templates reach terminal handlers; raw proposals/target lineage remain untrusted. Explicit workflow bodies are non-executing data. External function registration is disabled; resumed history is fail-closed. Worker prompts receive the signed menu directly. This is not general semantic taint tracking or per-model-call Go authorization.

The new Docker API works on 127.0.0.1:8443 -> container:8080, uses supported embedding none and local Ollama. Real model-selected Go probes produced three independently reproduced findings, but all three scoped flows waited after worker errors and were stopped. Read the full comparison report and MASTER_HANDOFF.md; the completed result is scoped integration enforcement, not a claimed full replacement. Grounding v2 produced equal off/on outcomes, not an effectiveness gain.

## TA alignment: Red Team / Blue Team allocation

TA Option A/B below name the reporting paths, separate from the older model-architecture Option A (shared Qwen across live roles).

KAYAN uses its existing security agents rather than adding a second team engine. Recon, Web-App and Network form the Red Team: they perform the bounded, TrustGate-governed tests in the live Python engagement. Reporting forms the Blue Team: it assembles the evidence-based report and defensive recommendations. Planner coordinates the live work and is not an additional offensive or defensive specialist. These are task-allocation labels, not new capability grants.

Phase 1 is a separate local retrieval function, `pentagi/risk_plan.py`. It reads optional descriptive engagement context and the existing pinned ATT&CK/OWASP index, then ranks up to three hypothetical matches by TF-IDF relevance. A priority is a text-match order, not measured risk, likelihood or severity. Missing context or no matches produces an explicit insufficient-context result. Phase 1 creates no agent, accesses no target, calls no model and performs no TrustGate authorization.

Option A feeds those hypotheses directly into the existing Reporting agent's structured report builder. Its shared mitigation synthesis uses authored defensive templates with local framework references; it performs no additional model inference, agent loop, target testing or authorization. It reports zero verified findings and labels its recommendations hypothetical. Option B retains the existing governed live engagement and feeds reproduced findings into the same mitigation section. Candidate/model claims without a supported verification record and audit reference do not enter that section. Reporting trusts the governed runtime's proof envelope; it does not independently re-run the proof when displaying a saved report. Hypotheses and verified findings remain different evidence bases, even though the report shape is shared. This resolves the Blue Team task-allocation item.

The intake accepts optional company size, departments, infrastructure summary, network architecture, data storage and customer touchpoints. **These fields carry zero policy weight.** They are held outside the signed ROE and flow only to Reporting's narrative framing; Phase 1 can separately analyze the same descriptions offline. They do not reach `policy.rs`, `roe.rs`, ROE signing/loading, `/authorize` or any Cedar evaluation input. Descriptions are untrusted data, not operator instructions, verified facts or scope authority. The new planning endpoints neither replace nor mutate the live console state.

The planning dialog adds Defense in Depth / Zero Trust as presentation filters, inclusion toggles and an additive illustrative point total. Points are arbitrary display weights, not prices, quotes or measured implementation effort. Selection is exported as presentation metadata and does not change original evidence, authorization or agent behavior. No billing or pricing engine exists. `docs/TA_DELIVERABLES_ALIGNMENT.md` records implementation evidence, commands and the separate pending browser acceptance.

## Training versus retrieval grounding: design decision and measured result

This project chose a pretrained local Qwen model plus retrieval rather than fine-tuning, to keep the work within its local compute and project-time constraints. This was an engineering scope decision, not a completed training experiment. No fine-tuning duration, faster-training winner or measured training-cost comparison is available. The pretrained model's role prompts, skill packets and retrieved context are not training. The existing reference index already combines MITRE ATT&CK and OWASP Top 10; a combined retrieval approach is implemented, not a third unbuilt framework. Individual queries can return either framework rather than necessarily both.

The recorded grounding-off/on engagements address the underlying agent-quality question more directly than an invented training-time estimate would: they observe bounded actions, evidence-supported findings and policy decisions under both conditions. They do not establish which fine-tuning approach would train faster. Historical results below were read from preserved artifacts during TA alignment; these engagements were not rerun for this documentation pass.

| Recorded condition | Findings / allowed / denied | Findings-based MITRE coverage |
|---|---|---|
| Original v1, grounding off | 1 / 23 / 1 | 20% |
| Original v1, grounding on | 0 / 23 / 2 | 0% |
| Bounded-retry v2, grounding off | 2 / 29 / 1 | 40% |
| Bounded-retry v2, grounding on | 2 / 29 / 1 | 40% |
| Separate scoped Go evaluation, with verifier authorizations | 3 / 19 / 15 | 40% |

Original v1 regressed with grounding; v2 produced equal outcomes. **No grounding improvement was demonstrated. Preserve this failure.** The v2 findings reproduced with independent fresh nonces (2/2), while the unchanged legacy evidence rubric scored 1/2 because its command criterion requires whoami rather than benign nonce echo. Those metrics do not measure blinded classification accuracy. Coverage uses five existing lab labels, not all ATT&CK; XSS is raw script reflection, not confirmed browser execution. The separate Go result reproduced 3/3 findings, scored 1/3 under the legacy rubric and includes three verifier ALLOWs (Go-only 16 allowed / 15 denied). Different signed command menus, inference gating and workflow decomposition prevent a causal Python-versus-Go or grounding-superiority claim. All three Go flows waited after worker failures and were stopped; the scoped enforcement evaluation remains complete with those limits disclosed.

The available evidence supports a working, bounded platform and an honestly negative/equal retrieval comparison. It does not support more accurate agents, reduced hallucination, faster training or effective mitigation merely because references were injected. Phase 1 and Option A add planning/reporting paths, not new evidence of grounding effectiveness. Source artifacts: `eval/reports/live_grounding_{off,on}.json`, `live_grounding_{off,on}_v2_bounded_retry.json`, their comparison reports, and `pentagi_go_governed_local_v3_worker_scope{,_verified}.json`.
